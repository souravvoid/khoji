# FILE_NOT_FOUND Analysis

## 1. Error Message

```
File not found: 1306bcf8-e625-4993-8d88-2cb34d1632ce
```

## 2. Root Cause

**Classification: Frontend state bug (data flow)**

The `filePath` field in the `ProcessingJob` interface is dual-purposed:
1. As a **tracking key** (a UUID generated by `crypto.randomUUID()`) for the processing queue
2. As the **actual filesystem path** to pass to `processDocument()`

When the user clicks **Retry** on a failed processing job, `ProcessingModal.tsx` passes `activeJob.filePath` (which is the UUID tracking key, not the real path) to `processDocument()`. The Tauri backend then tries to canonicalize this UUID string as a file path, which fails with `"File not found: 1306bcf8-..."`.

## 6. Filesystem Findings

No physical file associated with `1306bcf8-e625-4993-8d88-2cb34d1632ce` was expected to exist. The error is not caused by a deleted/moved/renamed file — it is caused by a UUID being passed where a file path was expected.

## 7. Reproduction Steps

1. Attempt to upload a file in a context where processing fails (e.g., `@tauri-apps/plugin-dialog` throws, or the file path is invalid)
2. The processing job is created with `filePath` set to a UUID (line 68 of `App.tsx`)
3. An error is displayed in the ProcessingModal
4. Click **Retry** on the failed job
5. **Result**: Error displayed: `"File not found: 1306bcf8-e625-4993-8d88-2cb34d1632ce"`

## 8. Fix Implemented

**Strategy**: Store the actual filesystem path in a separate `originalPath` field on the job, and use that for retry instead of the tracking UUID.

### Changes

**`frontend/src/stores/documentStore.ts`** — Added `originalPath?: string` to `ProcessingJob`:

```typescript
interface ProcessingJob {
  filePath: string
  filename: string
  originalPath?: string    // ← added
  progress: number
  stage: string
  status: 'queued' | 'processing' | 'complete' | 'error'
  error?: string
  docId?: string
}
```

**`frontend/src/App.tsx`** — Store the real file path in the job once obtained:

- Line 92: `originalPath: file.name` in the dialog-catch fallback
- Line 96: `originalPath: filePath` in the main processing call

**`frontend/src/components/processing/ProcessingModal.tsx`** — Use `originalPath` for retry:

```typescript
const path = activeJob.originalPath || activeJob.filePath
if (path) {
  // ...call processDocument(path) instead of processDocument(activeJob.filePath)
}
```

## 10. Final Status

**Resolved.** The fix prevents UUID tracking keys from being passed as file paths. The `originalPath` field cleanly separates the job tracking identifier from the filesystem path, and the retry mechanism now uses the correct path.

### Error Classification

**Frontend state bug** — The `filePath` property of `ProcessingJob` was overloaded to serve as both a unique state-tracking key (UUID) and a filesystem path. This ambiguity caused the retry flow to pass a UUID to the backend's file validation.
